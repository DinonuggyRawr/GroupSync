# GroupSync

GroupSync is a group availability matcher written in C. It helps organizers collect availability through Google Forms and find meeting times that work for the most participants.

The matching program runs on your Windows computer. A Google Apps Script backend creates a form, stores responses in a Google Sheet, and sends availability back to GroupSync through a PowerShell helper.

## How it works

1. Enter an event name, meeting duration, and possible dates and time ranges.
2. GroupSync creates an event-specific Google Form.
3. Share the form link with participants.
4. Participants enter their names and mark each 30-minute block **Available**, **Maybe**, or **Unavailable**.
5. GroupSync collects the responses and checks continuous time windows long enough for the meeting.
6. The program displays up to three ranked meeting recommendations.

Availability is evaluated across the entire meeting window, rather than individual time slots alone.

## Requirements

- Windows with Windows PowerShell 5.1.
- A C compiler, such as the Visual Studio C/C++ build tools.
- A Google account with access to Google Forms, Sheets, and Apps Script.
- An internet connection for creating forms and retrieving responses.

## Google API / Apps Script setup

This integration uses Apps Script's built-in Google Forms and Sheets services. You do **not** need to create a desktop OAuth client or manually enable the Google Forms API for this backend. Instead, authorize your own Apps Script project and connect GroupSync to its deployed web app.

### 1. Create the script project

1. Open [Google Apps Script](https://script.google.com/).
2. Select **New project** and name it **GroupSync**.
3. Open `code.gs` from this repository and copy its contents.
4. In the Apps Script editor, replace the default contents of **Code.gs** with the copied code.
5. Save the project.

The script belongs to your Google account. Forms and response spreadsheets created through it will also belong to that account.

### 2. Generate your API key

1. Select **setup** from the function dropdown.
2. Click **Run**.
3. Review and approve the Google permissions required by the script.
4. Open the **Execution log** and copy the generated API key.

Keep this key private. It authenticates your desktop program to your backend. It is generated by GroupSync's setup function, not by Google Cloud Console.

The supplied setup function stores the key in **Project Settings → Script Properties → API_KEY** and preserves it when setup runs again.

### 3. Deploy the backend

1. Select **Deploy → New deployment**.
2. Select the deployment type **Web app**.
3. Set **Execute as** to **Me**.
4. Set **Who has access** to **Anyone**.
5. Click **Deploy** and complete any authorization prompts.
6. Copy the **Web app URL** ending in `/exec`.

Use the deployed `/exec` URL, not the editor URL or development `/dev` URL. The endpoint is accessible publicly, while the script checks the API key before performing supported actions.

Some Google Workspace organizations restrict public web apps or external form responders. If these options are unavailable, consult your administrator or use an account whose policies allow them.

### 4. Connect the desktop program

1. Keep `groupsync_google_forms.ps1` alongside the program and run GroupSync from that folder.
2. On first run, enter the deployment URL and API key when prompted.
3. GroupSync tests the connection and saves the settings to `groupsync_google_config.json`.

If you previously used the desktop OAuth version, back up the old configuration outside the repository and remove the original configuration file before running setup again. The Apps Script helper expects `web_app_url` and `api_key`, rather than OAuth client credentials.

## Build and run

Install Visual Studio's **Desktop development with C++** workload, which includes the Microsoft C compiler. Open a **Developer PowerShell for Visual Studio**, change to the project directory, and run:

```powershell
cl /W4 /TC main.c availabilitymatcher.c /Fe:groupsync.exe
.\groupsync.exe
```

This command builds the terminal entry point supplied with the project. If the repository adds a separate GUI entry point, use that GUI project's Visual Studio build configuration instead.

## Create an event

Enter the event name, meeting duration, possible dates, and scheduling ranges. Times use 24-hour `HH:MM` notation on 30-minute boundaries. The end time must be later than the start time; `24:00` can be used as an end time.

Share the generated Google Form link, then enter how many responses to wait for. The terminal helper checks every 15 seconds. Once enough submissions arrive, it downloads the requested responses, closes the form to new submissions, and runs the matcher. Press **Ctrl+C** to stop waiting; stopping the desktop program does not itself close the form.

Open the response spreadsheet using the URL printed by the helper. Participants only need the form link.

## Event cancellation

If the repository's `code.gs` includes the `Cancel` action, it can stop a form from accepting new responses while preserving the form, spreadsheet, and submitted answers.

The desktop application and PowerShell helper must also send that action and stop polling when cancellation succeeds. Adding the server function alone does not add a working desktop Cancel button.

## Updating the backend

After editing the Apps Script code:

1. Save your changes.
2. Select **Deploy → Manage deployments**.
3. Edit the existing web app deployment using the pencil icon.
4. Select **New version**, then **Deploy**.

Updating the existing deployment keeps its URL. The API key also stays the same unless you change it in Script Properties. Creating a separate new deployment gives you a new URL that must be entered in the desktop configuration.

## Local generated files

| File | Contents |
| --- | --- |
| `groupsync_google_config.json` | Private deployment URL and API key. |
| `groupsync_event.json` | Event dates, time ranges, and duration. |
| `groupsync_form.txt` | Form ID and participant link. |
| `groupsync_responses.tsv` | Participant names and availability codes. |

The TSV format contains a participant name followed by `A`, `M`, or `U` values in date/block order.

Exclude credentials, generated data, and build output from Git. For the terminal version, add these entries to `.gitignore`:

```gitignore
groupsync_google_config.json
groupsync_event.json
groupsync_form.txt
groupsync_responses.tsv
*.exe
*.obj
*.pdb
*.ilk
.vs/
```

Keep any separately saved GUI event records out of Git as well.

## Limitations and privacy

- Each submission counts as one participant. Duplicate submissions are not automatically resolved by name.
- Time labels use the organizer's intended time zone; the original backend does not automatically convert participant time zones.
- The terminal workflow waits for the requested response count. Partial-response GUI updates require an additional nonblocking fetch workflow.
- The original terminal files represent one current event and may be overwritten by the next event. A multi-event GUI needs separate persistence.
- Responses remain in the organizer's Google Form and private Sheet. Avoid sharing the Sheet with participants unless you intend to reveal their responses.
- The hidden `_GroupSync` tab contains backend metadata. Do not change or delete it; hiding a tab does not protect its contents from spreadsheet editors.
- The local API key is stored in plaintext. Do not commit it, paste it into issues, or include it in screenshots. If exposed, replace `API_KEY` in Script Properties and update the desktop configuration.

## Troubleshooting

| Problem | What to check |
| --- | --- |
| Unauthorized request | The desktop API key must match the script's `API_KEY` property. |
| Unknown action | Confirm the action exists in `doPost`, then deploy the updated script version. |
| Google sign-in page instead of a response | Check the `/exec` URL and web app access setting. |
| Participants cannot open the form | Test the responder link signed out and review the form's responder access settings. Organization policies may restrict access. |
| Program keeps waiting | Confirm participants submitted the correct form and the requested response count is accurate. A manually closed form may leave the original helper waiting. |
| Old OAuth prompts or configuration errors | Use the Apps Script replacement helper and recreate the old local configuration. |
| Running `doPost` in the editor fails | `doPost` expects an HTTP request; run `setup` in the editor and test the deployed endpoint through the desktop helper. |
| Cancel does not work | Check the deployed `Cancel` branch, cancellation function, and desktop/helper support. |
